# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Projekt

**Eclipse Fennec Services** (Arbeitsname DDSR — Dynamic Distributed Service Registry). Cross-Language Service-Registry (Java + TypeScript): sprachunabhängiges, EMF/Ecore-basiertes OSGi-Service-Modell, Broker mit REST/SSE- und MQTT-Event-Transport, SDKs für Provider und Consumer in beiden Sprachen, Cross-Language-Harness. Migriert 2026-08-25 aus dem Prototyp-Repo `geckoprojects-org/ddsr` (Quelle: Branch `feat/ts-parity`); Tracking: Issue #1.

Maven groupId: `org.eclipse.fennec.services` (Quelle: `gradle.properties`, Single Source für Gradle und bnd). Default-Branch ist **`snapshot`**. Java **21**.

**Zwei Migrations-Festlegungen, die Code-Arbeit hier einschränken:**

1. **Wire-Namen sind eingefroren, bis der TS-Namespace-Rename kommt (Issue #4):** `ddsr.fingerprint`, `ddsr.provider.name/lang`, `ddsr.broker.transport`, Header `X-DDSR-Requestor`, MQTT-Topic-Prefix `ddsr/events`, SSE-Event-Name `ddsr-service-event`, Context-Path `/ddsr/rest`. Sie sind Cross-Language-Verträge mit dem TS-Code — einseitig umbenennen bricht die Harness.
2. **Der TS-Track behält sein Original-Naming** (`@ddsr/*`, `DDSRPackage`, `org/gecko/ddsr`-Pfade, `model/ddsr.ecore` als Dateiname) — Umbenennung macht ein Kollege separat. Der ECORE-INHALT ist synchron zum Java-Modell (nsURI `http://eclipse.org/fennec/services/1.0`, nsPrefix `services`); kanonische Quelle ist `org.eclipse.fennec.services.model/model/services.ecore`, die TS-Kopie wird von dort gesynct + mit `pnpm --filter @ddsr/model generate` regeneriert.

## Module

- `org.eclipse.fennec.services.model` — EMF-Codegen aus `model/services.ecore` nach **`src-gen`** (fennecEMF `-generate`; das persistierte GenModel wird NICHT auto-reconciled — bei Ecore-Änderungen manuell mitpflegen)
- `org.eclipse.fennec.services.api` — der Vertrag, auf den sich alles andere einigt: vier Rollen-Interfaces, Diagnostics, EventSink/EventDocument, LookupBackend, Exceptions, dazu die sd1/im1-Fingerprints, die Flavor-Konvention und `JavaContracts` (Vertrag aus einem Java-Interface ableiten, deterministisch). Keine Komponenten, keine Konfiguration. Bewusst **ohne** den XMI-Codec: ein Fingerprint wird über dem Modell im Speicher gerechnet, nie über serialisierten Bytes — und genau das erlaubt, den Codec nach emf.osgi zu spenden, ohne die eingefrorenen Draht-Schemata mitzugeben. `FrameworkShutdown.installFor` liegt hier als Hilfsklasse; installiert wird der Hook von den zwei Komponenten, die ohnehin einen Lebenszyklus führen (Broker und Client)
- `org.eclipse.fennec.services.runtime` — die beiden Runtime-Services (`BrokerRuntime`/`ClientRuntime`, DTOs) und `ChangeCountPublisher`; seit #187 eigenes Bundle **ohne** das EMF-Modell, damit eine Anwendung, die nur einen Change-Count-Service will, nicht Modell, Fingerprints und Rollen-Interfaces mitinstallieren muss. Seit #188 nimmt der Publisher zusätzliche Service-Properties an und trägt sie durch jedes Update (`setProperties` ersetzt, statt zu mergen)
- `org.eclipse.fennec.services.broker.core` / `broker.rest` / `broker.mqtt` — der Broker selbst, JAX-RS/SSE, MQTT-EventSink. `DdsrBrokerImpl` ist seit #110 nur noch Fassade; dahinter je ein Belang (`BrokerState`, `Registrations`, `CatalogStore`, `Lookups`, `UpdatePolicies`, `Liveness`, `Sessions`, `ColdCache`, `Announcements`), und `Retirement`/`Republication` sind die zwei Nähte, über die sie einander aufrufen. Alle drei Broker-Verträge werden seit #88 generisch serviert — die Regel, was mit einer Antwort reist, macht die mehrwurzelige Lookup-Antwort beschreibbar, `BrokerLookupRest` ist der Adapter mit der Signatur, die der Vertrag beschreibt. Handgeschrieben bleibt nur `EventsResource`: SSE ist kein Aufruf
- `org.eclipse.fennec.services.cloudevents` — die Hülle: CloudEvents 1.0 über dem `io.cloudevents.model`-Ecore, beide Content-Modi (structured JSON für MQTT/SSE, `ce-*`-Header über HTTP). Kennt CloudEvents und nichts über Payload-Kodierung — die bleibt die Wahl des Vertrags (#100): die Nutzlast ist, was `Resource.save` für den Content-Type liefert (Factory aus der Content-Type-Registry des `ResourceSet`: XMI, Protobuf, JSON über emf.codec), und die Hülle sagt nur womit (`datacontenttype`) und wovon (`dataschema` = nsURI des Pakets der Wurzel, nie eine EClass-URI — absolute URI ohne Fragment; im structured mode immer, über HTTP als `ce-dataschema`, wenn Body bzw. Antwort ein Modellobjekt ist). **Über MQTT/AMQP schreibt und liest die Hülle seit Schritt 2 die Messaging-Instanz** (`cloudEvents=structured`, `Envelopes` im Link-Bundle übersetzt zwischen unserem CloudEvents-Modell und Messagings Kontext; `replyto`/`correlationid` sind dort Reply-Kanal und Korrelation der Nachricht) — XMI reist dort als `data_base64`, der TS-Track schreibt weiter seine eigene Hülle mit String, beide lesen einander; unser `CloudEventCodec` schreibt nur noch für SSE. Wie die Bytes in der JSON-Hülle liegen, folgt dem JSON Event Format §3.1, in Java und TS gleich: JSON-Content-Type → **direkt als JSON-Wert** in `data` (nie als String), anderer Text (XML) → String, sonst `data_base64`; gelesen werden alle drei, dazu XML als Base64 (so schreibt es Gecko Messaging) und ein in einen String verpacktes JSON-Dokument (so schrieben wir es vorher); die Nutzlast reist als Bytes, weil ein Event-Dokument mehrwurzelig ist und `data : EObject` nur eines hält
- `org.eclipse.fennec.services.xmi.codec` — Wire-Codec: die Kodierung wird seit #100 per Content-Type aus der ResourceSet-Factory-Registry gewählt (XMI als Vorgabe, Protobuf über emf.util), ein nicht registrierter Content-Type wird abgelehnt statt still als XMI geschrieben; die Härtung hängt am Format, nicht am Codepfad. Die Lesegrenze (`WireBody.MAX_BYTES`, 1 MiB) ist seit #219 Vorgabe statt Konstante: `max.body.bytes` an `provider.rest`, `rsa.distribution.rest`, `provider.messaging.connection`, `client.messaging.invoker` und an der RSA-Rolle (leitet in die drei ab); über Messaging setzt `LinkSettings.carrying` dazu `maxMessageSize` der Instanz (Dokument × 4/3 + Hülle). Nicht abgedeckt: Antworten, die der REST-Client liest. Der Klassenname ist zu eng und bleibt vorerst
- `org.eclipse.fennec.services.client.java` / `client.rest` / `client.messaging` — transport-agnostisches SDK + Transporte. **Der Client wartet auf seine Invoker:** `InvokerRegistry` ist das eine Whiteboard über alle `ServiceInvoker` und registriert sich selbst als `InvokerProvider` mit der Eigenschaft `fennec.invokers` (Flavor-Namen; erst eintragen, dann veröffentlichen, beim Gehen umgekehrt). `DdsrClient` hat darauf eine „virtuelle“ Referenz (`@Component(reference = …)`, Name `invokers`, nie injiziert) mit `invokers.target` — dieselben Flavors wie `supported.flavors`, z. B. `(&(fennec.invokers=REST)(fennec.invokers=MQTT))`; ohne Invoker für jeden davon gibt es keinen Client und der Broker erfährt nichts. Der Client hat deshalb `ConfigurationPolicy.REQUIRE`. Die Proxy-Factory bindet den `InvokerProvider` mandatory/static ohne Target. Die RSA-Rolle leitet das Target ab, die Beispiel-Konfigurationen schreiben es direkt
- `org.eclipse.fennec.services.client.tests` — das erste OSGi-Testprojekt (`testOSGi`, org.osgi.test, läuft in `./gradlew build` mit): das Client-SDK allein im Framework, der Test spielt den Transport (Broker-Proxies, EventSource, Invoker als Fakes) und prüft, was DS mit `invokers.target` macht — ohne Konfiguration kein Client, bei fehlendem Invoker `UNSATISFIED_REFERENCE` auf `invokers`, Client kommt mit dem letzten Invoker und geht mit ihm. Falle: ein Lambda ohne Capture ist **eine** Instanz, zwei Fake-Invoker müssen zwei Objekte sein. `build.gradle` zeigt `testOSGi` auf das aufgelöste bndrun
- `org.eclipse.fennec.services.rsa` / `rsa.distribution.rest` / `rsa.distribution.messaging` / `rsa.discovery.rest` / `rsa.discovery.mqtt` / `rsa.discovery.local` / `rsa.topology` / `rsa.config` — OSGi Remote Service Admin auf DDSR (#24); der OSGi-RSA-TCK läuft grün (`org.eclipse.fennec.services.rsa.tck`, `./itest/run-tck.sh`): Kern mit zwei SPIs (`FlavorDistribution`, `ServiceDiscovery`), je Flavor ein Provider über RSA-Config-Types, lokale Service-Registry auf der EObject-Registry; `examples.rsa.api` / `examples.rsa` / `examples.rsa.consumer` sind der Beweis: ein simpler OSGi-Service, in einem Framework exportiert und in einem anderen per `@Reference` gebunden — ohne Vertragsdokument. Importierte Proxies registriert ein leeres Host-Bundle (`ProxyHost`), nicht das RSA-Bundle: das scheiterte am Class-Space-Check. Konfiguriert wird ein Knoten über **eine** Rolle (`rsa.config`: PID `…rsa.provider` bzw. `…rsa.consumer`), aus der eine Konfigurationskomponente die einzelnen PIDs ableitet, prüft, in fester Reihenfolge schreibt und in der Gegenrichtung abräumt (#109) — die neun handgeschriebenen Konfigurationen sind damit Implementierungsdetail
- `org.eclipse.fennec.services.telemetry` — OpenTelemetry hinter den beiden Nähten (#126): `CallTracer` (W3C-Kontext über REST-Header bzw. CloudEvents-Extensions), die Runtime-Services als Gauges und die JUL-Brücke, die Logzeilen mit dem Span korreliert. Bringt eigene W3C-Propagatoren mit, weil die OSGi-Technology-Integration einen Noop registriert — als Service `W3cPropagators` (`fennec.propagators=w3c`, niedrigstes Ranking), den `OtelCallTracer` mandatory/static bindet; welche Propagatoren ein Knoten nimmt, sagt `propagators.target` (der Schalter `useRegisteredPropagators` ist entfallen); die otel-Bundles kommen als Snapshot von Central
- `org.eclipse.fennec.services.security.jwt` — Bearer-Token-Verifikation (Scheibe 1 der Durchsetzung, siehe [docs/SECURITY.md](docs/SECURITY.md) §7a): `JwtVerifier` als Naht, `NimbusJwtVerifier` konfiguriert wie ein `BearerTokenScheme` und nur per Konfiguration aktiv, `BearerAuthFilter` auf jeder Application mit `fennec.auth=bearer`, `NoAuthFilter` für `fennec.auth=none`, `CallPrincipal` im api-Bundle als Zwilling von `CallOrigin`. Eine Application nennt ihren Modus zweimal (`fennec.auth` + `extension.select` auf `fennec-auth-<mode>`), sonst liefe bearer ohne Verifier ungeschützt. Seit Scheibe 2 tragen alle vier REST-Applications des Brokers den Modus aus **einem** Platzhalter (`DDSR_AUTH_MODE` → `fennec.auth.mode` → `bearer`); `BrokerApplication` ersetzt dafür die `.default`-Application, die Eigentumsregel liegt in `broker.core/Ownership`. `broker.bndrun` sagt ausdrücklich `none` (Entwickler-Broker), das Image ausdrücklich `bearer` — es erbt sonst das `none` des exportierten Launches. Der Verifier kommt seit Scheibe 4 aus der Umgebung (`DDSR_JWT_ISSUER`/`_JWKS_URI`/`_AUDIENCES`/`_SCOPE_CLAIM` in der Broker-`config.json`) und registriert sich nur mit Issuer — leer heißt kein Verifier, ohne Fehler. `RolesAllowedFeature` setzt `@RolesAllowed`/`@PermitAll` auf JAX-RS-Ressourcen durch (Applications mit `fennec.auth=bearer*`), mit der Modell-Semantik: **alle** Rollen nötig (Jakarta liest sie als Alternativen), `"**"` = irgendein verifizierter Aufrufer — genau das schreibt das m2t-Resource-Template. Domain v1: ein Broker je Domain, `DDSR_DOMAIN` wird an Registrierung und Session geschrieben, fremde Tokens fängt schon Issuer+Audience des Verifiers ab. Aus dem Timetracking-Prototyp gehoben; zieht nach emf.util um, sobald es einen zweiten Nutzer gibt (README im Bundle)
- `org.eclipse.fennec.services.security.mtls` — der zweite Modus, `fennec.auth=mtls` ([docs/SECURITY.md](docs/SECURITY.md) §7d): `MutualTlsAuthFilter` (Prototype-Komponente, weil die per `@Context` injizierte `HttpServletRequest` nur in der Application gilt, die sie injiziert hat) macht aus dem Client-Zertifikat denselben `VerifiedPrincipal` wie der Bearer-Filter — Subject = CN, Issuer = DN der CA, Rollen aus `DDSR_MTLS_ROLES` (`subject=rolle,rolle`, Einträge per `|`). Zertifikat aus der TLS-Sitzung (Felix Jetty, `DDSR_HTTPS_*`, `clientcertificate=needs`) oder aus einem Gateway-Header, nur von den konfigurierten Adressen. Falle: `delimiter=;` im Interpolations-Platzhalter ist leer (der Direktiven-Parser trennt selbst an `;`) und das Plugin läuft in einen OOM — deshalb `|`. Der Java-Client zeigt Keystore/Truststore (`tls.*` am `client.rest`, `DDSR_TLS_*`). Kombinierbar: Discovery per Zertifikat, Aufrufe per Token — am Java-Client `broker.tokens.target=(fennec.tokens=none)` bei `provider.tokens.target=(fennec.tokens=oauth)` (kein Broker-Token, Provider bekommen weiter Tokens je Audience; an der RSA-Rolle und in TS weiter `broker.authentication=certificate`), eine aus Konfiguration servierte Distribution kündigt das Scheme an, das ihr Dokument nicht tragen kann; Konvention CN = OAuth-Client-ID. Beweis: Host-Harness-Szenario M mit pro Lauf erzeugter CA (`itest/tls/make-certs.sh`), abgesichert inkl. `PersonStore` per Zertifikat angemeldet und per Token aufgerufen. RSA: `NodeIdentity` trägt Keystore/Truststore und `brokerByCertificate`, `rsa.config` leitet `tls.*`/`broker.authentication` in `client.rest` ab; Szenario M fährt den Ledger aus K so über den mtls-Broker. TS: `tlsFetch` als Client, `createCertificateVerifier` + `restDispatcher({ certificates })` als Provider. **MQTT:** jede MQTT-Verbindung (`broker.mqtt`, `client.mqtt`, `client.messaging.invoker`, `provider.messaging.connection`) nimmt dieselben vier `tls.*`-Attribute und reicht sie an ihre Messaging-Instanz weiter (`MessagingLink`), nur bei `ssl://`; der Invoker antwortet mit Keystore unter dem CN, TS-Transporte nehmen `tls` (`pfx`/`ca`) und `consumer`. Durchsetzung macht der Messaging-Broker (`use_identity_as_username` + ACL auf getrennten Request-/Reply-Bäumen); Beweis Podman-Szenario Q inkl. Lauscher mit fremdem Zertifikat, der nichts empfängt
- `org.eclipse.fennec.services.security.oauth` — die rufende Hälfte (Scheibe 4): `ClientCredentialsTokens` holt per Client-Credentials-Grant das Token, das ein Knoten dem Broker zeigt, cached es und erneuert 30 s vor Ablauf; registriert `TokenSupplier` (api-Bundle) nur mit `token.uri`, also per `DDSR_OAUTH_*` aus der Umgebung abschaltbar. `RestTransport` setzt den Header **nur** auf Aufrufe unter der Broker-URL — derselbe Client ruft Provider, und ein Broker-Token darf dort nicht wiederverwendbar landen. **Welchen Supplier der Transport bindet, sagt seine Konfiguration als Target der Referenz:** jeder Supplier meldet sich mit `fennec.tokens` an (`oauth`, `none` = `NoTokens` in `client.rest`), `RestTransport` hat zwei Referenzen, mandatory und static, `broker.tokens.target` und `provider.tokens.target` (Vorgabe `(fennec.tokens=none)`); der Invoker fragt den Transport. Vorher optional/dynamic — ein Knoten rief vor seinem Supplier ohne Token (401 in der CI zu #230). Der Transport hat deshalb `ConfigurationPolicy.REQUIRE`: ein statisches Target, das sich ändert, baut die Komponente neu, und ein auf Vorgaben gestarteter Transport riss so auf jedem zur Laufzeit konfigurierten Knoten (RSA-Rolle) die ganze Client-Kolonne mit — ohne `client.rest`-Konfiguration gibt es keinen Transport. `broker.authentication` am Transport ist entfallen (Zertifikat = Broker-Target `none`, Provider-Target `oauth`), die RSA-Rolle behält ihr Attribut und leitet die Targets ab; in den Beispiel-Konfigurationen kommen sie aus `DDSR_TOKENS`/`DDSR_BROKER_TOKENS`. TS-Zwilling: `tokenSupplier`/`clientCredentials` in `@ddsr/client`, nur um den Broker-fetch gewickelt. Auf einem bearer-Broker muss die `consumerId` der Name aus dem Token sein (bei Keycloak `azp`)
- **Rollen pro Operation (Scheibe 3):** das Modell behält `SecurityRequirement.scopes`, Rollen kommen über `scope.claim=realm_access.roles`. `SecurityRequirements` (api, `common`) ist die eine Regel „Operation, sonst Interface“; `RestDispatcher` prüft nur in bearer-Applications (401/403), `ServedSecurity` entscheidet den Modus — aus der Konfiguration (Vertrag mit Requirement ohne `fennec.auth` wird nicht serviert) oder aus dem Flavor-Scheme (RSA-Weg: `bearer` bzw. `bearer-optional`, wenn `@PermitAll`-Operationen dabei sind; ohne Scheme verweigert, MQTT ebenso). `JavaContracts` liest `@RolesAllowed`/`@PermitAll` (`@DenyAll` verweigert) per Namen ohne jakarta.annotation-Abhängigkeit. Broker-Rollen-Matrix (§3/§7c): `service-provider` / `service-consumer` / `service-admin` stehen als Requirements in den drei Broker-Dokumenten, `BrokerRoles` prüft die handgeschriebenen Resources; der `BrokerSelfPublisher` hängt das Scheme an die eigenen Flavors (bearer: Issuer, none: `ConnectionScheme`), sonst lehnt das Validierungstor die Selbstanmeldung ab; `@ddsr/stubs` werden bei Änderungen der Broker-Dokumente aus der Katalog-Kopie neu generiert. `TokenSupplier.token(audience)` = Scope gleichen Namens, Token pro Scope; Broker-Token mit `scope=ddsr-broker`. RSA: `rsa.config` nimmt die Knotenidentität (`NodeIdentity`) und leitet OAuth-, JWT- und Distributions-Konfiguration ab, Intent `fennec.bearer`; Beweis ist Harness-Szenario K (`Ledger` in `examples.rsa.api`)
- `org.eclipse.fennec.services.flavor.rest` — die REST-Platzierungsregeln, geteilt von Consumer, Dispatcher und Template (kein JAX-RS)
- `org.eclipse.fennec.services.messaging` — die Verbindung aller MQTT-Teile (#218): `MessagingLink` ist eine Gecko-Messaging-Instanz (`org.gecko.messaging`, Branch `osgitech`, nur Snapshot; Binding nach URL-Schema: `mqtt3` oder `amqp`) je Broker-URL, als Factory-Konfiguration aus der Konfiguration ihres Besitzers abgeleitet (`broker.url`, `client.id`, `tls.*`) und mit ihm wieder gelöscht — die Besitzer sind `broker.mqtt`, `client.mqtt` (Events), der Invoker und `provider.messaging.connection`, Paho importiert bei uns niemand mehr. Die Instanz läuft mit `cloudEvents=structured` und schreibt die Hülle selbst; der Link reicht Hülle (unser CloudEvents-Modell) und Dokument getrennt durch (`CloudEventCodec.Message`). **Client-ID:** ohne `client.id` in der Konfiguration ist sie `<rolle>-<erste 8 Zeichen der Framework-UUID>` (`LinkSettings.clientId`; `ddsr-consumer-…` am Event-Transport des Clients, `ddsr-broker-…` am Broker) — die feste Vorgabe `ddsr-consumer` teilten sich zwei Knoten, und ein MQTT-Broker trennt die ältere von zwei Verbindungen mit derselben ID, sodass sie einander abwechselnd hinauswarfen; Invoker und Provider-Verbindung hatten schon je Verbindung eine eigene. Reconnect und Wiederherstellen der Subscriptions macht die Instanz; der Client-Event-Transport zieht bei jedem Connect einen Snapshot. **Falle, die den Zuschnitt bestimmt:** SCR aktiviert die Instanz auf dem einen Thread, der Konfigurationsereignisse zustellt — wer in `activate` auf sie wartet, wartet auf sich selbst. Deshalb wartet der Link nie: `subscribe` ist ein Wunsch, `onConnected` die Nachricht; der Broker-Sink registriert sich mit der ersten Verbindung, `GenericMessagingDistribution` meldet erst nach `Served.whenListening` an, und `MqttDistributionProvider` (RSA) bietet sich erst mit stehender Verbindung als Service an (`MessagingDistribution.hold`). Nur der Invoker wartet synchron (`awaitConnected`), also nicht aus einem `activate` heraus zum ersten Mal einen neuen Broker rufen. Welches Binding gebraucht wird, sagt jeder Besitzer selbst (`@RequireMessaging(protocol = "mqtt3")` bzw. `"amqp"` an der Komponente, brauchbar seit org.gecko.messaging#23), der Link nur, dass er eines braucht. Braucht Configuration Admin im Launch
- **Der Messaging-Transport** — `flavor.messaging` / `client.messaging` / `provider.messaging` / `rsa.distribution.messaging`: alles, was über einen Messaging-Broker reist, ist **ein** Transport und im Modell **ein** Flavor (Grundsatz des Users, 2026-11-10: über Messaging ist die API für MQTT und AMQP gleich, verschieden sind nur Konfiguration und Abhängigkeiten). `MessagingFlavor` (`brokers`, `channel`, `replyChannel`, `exchange`, `defaultQos`) und `MessagingOperationFlavor` (`channel`, `replyChannel`, `qos` unsettable) ersetzen seit Schritt 2b `MqttFlavor`/`AmqpFlavor`; das Protokoll ist die `kind` des Flavors (`MQTT`/`AMQP` — bewusst zwei Literale, weil ein Lookup nach den Arten filtert, die ein Consumer spricht, und die RSA-Typen `fennec.mqtt`/`fennec.amqp` daran hängen) bzw. für einen Flavor ohne `kind` das Schema seiner Broker-URL. Es entscheidet nur, wie ein Kanal geschrieben wird (`/` und Topics gegen `.` und Routing-Keys, QoS-Obergrenze 1 bei AMQP). `MessagingFlavors` sind die Regeln (eingefrorene Konvention, TS rechnet dieselben Namen), `MessagingRoute` liest einen Flavor einmal. **Antwortweg ist eine Aussage des Flavors, je Operation:** `replyChannel` gesetzt → der Consumer hört auf seinem Teilbaum darunter und nennt den Kanal im Aufruf (dagegen lässt sich eine Broker-ACL schreiben, Szenario Q); leer → die Verbindung des Consumers stellt den Antwortkanal (Java: `MessagingLink.request` über Messagings `ReplyToPublisher`, Korrelation = `id` der Anfrage; TS: eigener Baum `ddsr/reply/<consumer>`). Die Provider-Seite kennt den Unterschied nicht: `MessagingLink.serve` reicht dem Dispatcher immer ein `Reply`. Dahinter ist alles einmal geschrieben: `MessagingServiceInvoker` (ein `ServiceInvoker` mit `ddsr.flavor={MQTT,AMQP}`), `MessagingDistribution` + `MessagingOperationDispatcher` und `GenericMessagingDistribution` (der Zwilling von #84: Factory-PID `…provider.messaging`, `messaging.broker` ist die einzige Deployment-Angabe; beim Herunterfahren erst zurückziehen, dann die Subscription schließen, FR-P3). RSA: je Konfigurationstyp ein kleiner Provider (`MqttDistributionProvider`, `AmqpDistributionProvider`, PIDs `…rsa.distribution.mqtt`/`.amqp`), der nur den Flavor baut; die Rolle kann die Kodierung nennen (`encoding`, z. B. `application/json` mit emf.codec im Launch). PIDs: `…client.messaging.invoker`, `…provider.messaging.connection` (jeweils `username`/`password`/`tls.*` — Zugangsdaten nie in der Broker-URL, der Flavor kündigt sie an); der Event-Transport heißt weiter `…client.mqtt`, weil Events nur über MQTT reisen. Welches Protokoll ein Launch spricht, entscheiden die Bindings, die er trägt (`org.gecko.messaging.mqtt3` + Paho bzw. `…amqp` + RabbitMQ-Client + Netty 4.2 neben dem 4.1 von grpc). Im TS-Track heißt das Paket weiter `@ddsr/transport-mqtt` und spricht nur MQTT (`canHandle` lehnt einen AMQP-Flavor derselben Klasse ab). Broker-Events über AMQP und AMQP im TS-Track gibt es nicht; ein Knoten mit `flavor=fennec.amqp` kündigt und hört über REST (`RsaSettings.effectiveDiscoveryFlavor`). Beweis: Podman-Szenarien E (TS, Flavor ohne Antwort-Baum), I, J, Q (MQTT, Q mit ACL auf dem benannten Baum), R und S (AMQP, S als JSON)
- `org.eclipse.fennec.services.provider.rest` — generische REST-Distribution: eine Factory-Konfiguration serviert einen Vertrag aus seinem Modell und meldet ihn optional selbst an (#84). Seit #204 in FR-P3-Reihenfolge: `GenericRestDistribution` registriert ihre Application **selbst** (`service = {}`), weil DS sie erst nach `activate` registriert und vor `deactivate` wegnimmt. **Servieren und Anmelden sind zwei Komponenten:** die Distribution registriert einen `ServedContract` — eine OSGi-`Condition`, Eigenschaft `publish` erst `false`, `true` sobald eine Whiteboard-Runtime die Application im DTO listet (`Deployment.of`, ausgelöst über `service.changecount`) — und leitet die Konfiguration von `ContractAnnouncement` ab (Factory-PID `…client.announcement`, Target `(&(fennec.distribution=<pid>)(publish=true))`). `ContractAnnouncement` und `ServedContract` liegen in `client.java` (Paket `client.announce`) und sind **für REST und Messaging dieselben** — `GenericMessagingDistribution` hebt die Condition, sobald der Messaging-Broker die Subscriptions hat (`Served.whenListening`); verschieden ist nur, was ein Transport vor der Anmeldung in den Flavor schreibt. Die Anmeldung bindet Condition, `DdsrClient` und `BrokerCatalog` mandatory/static, meldet in `activate` an und zieht in `deactivate` zurück; die Reihenfolge macht DS. Falle dabei: die Condition darf **nicht** `ddsr.contract` tragen, sonst findet der Dispatcher sie als Implementierung des Vertrags. Der RSA-Pfad (`RestDistributionComponent`) wartet dafür synchron (`awaitDeployed`)
- `org.eclipse.fennec.services.m2t` — die Templates sind das Produkt, die eingecheckte Ausgabe beweist nur, dass sie kompilieren: Interface je Vertrag, JAX-RS-Ressource je RestFlavor und seit #25 `service-publisher.mtl` — eine Komponente je Implementierung, die in der FR-P3-Reihenfolge anmeldet und zurückzieht und den Vertrag **nicht** in Code wiederholt, sondern aus dem Dokument liest. Zwei Fallen beim Erweitern: eine Generation braucht ein eigenes `output`-Verzeichnis (bnd leert es vorher) und ein Template sieht nur, was sein Modul `extends` — ein Query aus einem anderen Template ist kein Fehler, sondern erzeugt stillschweigend gar nichts
- `org.eclipse.fennec.services.examples.payment` / `examples.model` / `examples.persons` — Demo-Provider + Beispielmodell + der Consumer des `PersonStore`-Vertrags, dessen Rumpf ein Modell ist und dessen Kodierung Protobuf (#100); eigenes Bundle, weil das SDK nicht von einem Beispielmodell abhängen darf und der Provider seine Konfiguration mitbringt
- `org.eclipse.fennec.services.telemetry.rest` — Whiteboard-Extension (`ContainerRequestFilter`/`ContainerResponseFilter`), die handgeschriebenen JAX-RS-Ressourcen denselben Server-Span gibt, den der generische Dispatcher schon hat. Trifft die Default-Application, also genau dort, wo eine blanke `@JakartarsResource` landet — und bewusst **nicht** die benannten Applications der generischen Distribution (die bringen eigene Provider mit, #125), damit ein Aufruf einmal getract wird. `text/event-stream` wird ausgelassen: ein Abonnement ist kein Aufruf
- `org.eclipse.fennec.services.demo.telemetry` / `demo.traffic` — Demo-Gerüst für die Präsentation: die Konfiguration, die das OTel-SDK auf den Collector zeigen lässt (ein Bundle, weil `configurator.initial` zu früh gelesen wird), und ein Consumer, der auf einem Timer ruft (`ConfigurationPolicy.REQUIRE`, also still, wo ihn niemand konfiguriert). Die zugehörigen Launches sind `broker-otel.bndrun`, `payment-provider-otel.bndrun`, `client-otel.bndrun` — je ein `-include` des echten Launches plus ein handgepflegtes `-runbundles.otel`-Delta (ein Resolve würde die absichtlich mitgeführten Bundles verwerfen)
- `demo/observability/` — der Stack (Collector, Tempo, Prometheus, Loki, Grafana als podman-Pod, aus dem OSGi-Technology-Projekt übernommen) plus `run-demo.sh`, das Stack und alle drei Frameworks startet; in `gradle.properties` via `bnd_exclude` vom bnd-Build ausgenommen
- `ddsr-ts-client/` — TypeScript-Track. Provider-Seite seit #154 ohne Transportcode: `restDispatcher(flavor, objekt)` liest jedes Argument dort, wo der Flavor es hinschreibt (der Zwilling von `RestDispatcher`), `operationHandlers(vertrag, objekt)` leitet die MQTT-Handler aus dem Vertrag ab. Seit #154 komplett auch der Vertrag: `examples/payment/payment-provider.xmi` (Vertrag, Implementierung mit getypten Properties, REST- und MQTT-Flavor), `loadPaymentProvider` setzt nur Name, Adresse und ob MQTT; ein Test im Beispiel (jetzt vitest-Projekt) hält den sd1 gegen die Golden-Fixture. Telemetrie-Naht wie Java (#146): `@ddsr/telemetry` (nur die Naht, keine Abhängigkeiten), `@ddsr/telemetry-otel` (OTLP/HTTP über das Node-SDK), `withTracing` als Zwilling von `RestTransport.send` und ein Span um jede Invocation im REST-Flavor-Plugin. Serviceseite seit der Security-Welle: `createJwtVerifier` (RS256 über WebCrypto, keine Abhängigkeit) und `restDispatcher(…, { verifier })` prüfen Rollen pro Operation wie Java (401/403, `bearer`/`bearer-optional`, ohne Verifier bzw. Scheme nicht gebaut, außer `auth: 'none'`); Beweis ist Harness-Szenario T (`ledger-ts.ts`). mTLS als Client: `tlsFetch` (`@ddsr/client`, `node:https`, keine Abhängigkeit) in jede `fetchFn`-Naht; Broker per Zertifikat heißt in TS: Client ohne `tokenSupplier`, Plugin mit; die Beispiele lesen `DDSR_TLS_KEYSTORE` (PKCS12), `DDSR_TLS_CA` (PEM), `DDSR_BROKER_AUTHENTICATION`. ## Konventionen

- **`src-gen`-Ordner sind generierter Code** — nie von Hand editieren; aus `.ecore`/`.genmodel` regenerieren. Ecore-Änderungen macht grundsätzlich der Modell-Owner (User) bzw. nur auf dessen explizite Anweisung.
- **Im Java-Code immer `import`-Anweisungen verwenden** — nie voll qualifizierte Klassennamen im Code-Body.
- **Logging mit JUL** (`java.util.logging.Logger`), nicht `System.Logger`/slf4j; `System.out/err` nur begründet auf JVM-Shutdown-Pfaden (JULs Cleanup-Hook resettet den LogManager — DECISIONS_PARITY D14) und in Demos. INFO = Lifecycle, WARNING = Probleme, FINE = Diagnose.
- **Keine `Bundle-Version` in bnd.bnd** — die fennec-Library besitzt die Version (`base-version` in `cnf/ext/fennec.bnd`).
- **Commits immer mit** `Signed-off-by: Mark Hoffmann <m.hoffmann@datainmotion.com>` (Eclipse DCO).
- Teststrategie: plain JUnit 5 + AssertJ (Fakes oder Mockito — beides erlaubt), OSGi-Runtime nur wo OSGi selbst getestet wird; TS: vitest mit Fakes über die `fetchFn`-/Client-Seams. Die Harness ist der End-to-End-Anker.
